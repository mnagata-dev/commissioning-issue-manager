# CIM 複数PC同期機能 設計方針書（案）

- 作成日: 2026-10-15
- 状態: 方針整理（実装仕様・実機挙動は未検証）
- 対象: 既存CIMへの将来の同期機能追加

## 1. 目的と前提

複数のWindows PCで同一のホテル・プロジェクト・Issueを扱い、各PCはネットワーク断中もローカルSQLiteで業務を継続する。中央アプリケーションサーバーは設けない。共有ストレージには会社のSharePoint上のCIM専用フォルダーを利用し、Windows OneDrive同期クライアントを介してファイルを交換する。対象は当面社内ユーザーのみ、原則1ユーザー1PC。Microsoft 365管理者によるGraph APIアプリ登録は前提としない。

SharePoint/OneDriveは非同期のファイル転送手段であり、トランザクションDB・メッセージキュー・分散ロックではない。ローカル保存、同期フォルダーへの書き出し、他PCへの到達、SharePointへのアップロード完了は別の状態として扱う。

## 2. 論理構成

```text
PC-A: CIM(FastAPI) ─ SQLite / Outbox / Attachment Cache
                   └ OneDrive同期フォルダー ─┐
                                              SharePoint: CIM-Shared
PC-B: CIM(FastAPI) ─ SQLite / Outbox / Cache ─┘
```

共有フォルダーの概念的な構成（名称・階層は未確定）:

```text
CIM-Shared/
  changes/<device-id>/      # デバイス別の不変バッチ
  snapshots/                # 復元用スナップショットとメタデータ
  attachments/              # 不変の添付ファイル実体
  backups/<device-id>/      # バックアップ（同期用データとは論理分離）
```

## 3. 同期データと端末固有データ

- 全PCで同期: ホテル、プロジェクト、部屋、エリア、設備等のマスター、Issue、Comment、添付ファイルのメタデータ、変更履歴、削除・統合・競合解決イベント。
- 添付ファイル実体: プロジェクト×PC単位でオフライン保存A（全件ローカル）またはB（必要時取得）を選択。全体・ホテル単位の一括選択とプロジェクト単位の設定を提供する。
- 端末固有: オフライン保存設定、画面表示設定、ローカルバックアップの管理情報など。
- PC固有のIDと、端末間で共通の業務データID（UUID等）を区別する。

**業務同期検証前の未決事項:** User・Roleの同期範囲、Userの共通IDと各PCでの登録者・更新者等の参照解決を設計し、検証項目・合格基準を定める。Roleを同期する場合は、オフライン中の並行変更を含めAdministratorを最低1人維持する制約の検証も必要とする。現時点では方式を確定しない。

## 4. 変更イベントと配信

1. 業務変更と送信待ちイベント（Outbox）をローカルSQLiteの同一トランザクションで永続化する。
2. 短い待機時間で変更を束ね、最大待機時間に達したらデバイス別の不変バッチ（候補: JSON Lines）を確定する。秒数・件数は検証で決める。
3. 完成前のファイルを同期対象として公開しない。ファイル名・バッチIDは衝突しないようにする。
4. 受信側は形式、ファイル完全性、イベントID、依存関係を検証して冪等に適用する。未到着の依存イベントや未対応形式は保留する。
5. エラーは再試行し、破損・不正形式は隔離する。Issueのローカル編集は可能な限り継続する。

**検証課題:** ローカルの原子的なリネームが、OneDriveを介した他PCからの完全な公開を保証するわけではない。公開完了を示すマニフェスト、サイズ・ハッシュ検証、再試行などのプロトコルを検証して決定する。

## 5. 競合・重複・削除

- 異なるフィールドの独立した編集は原則自動統合。同一フィールドの並行編集は競合として保留し、いずれかのCIMユーザーが解決する。解決もイベント化する。
- 自動統合後の結果は適用前にService層で業務ルールの整合性を検証する。Target Type・Room・Targetの組み合わせ等が不成立の場合は適用を保留する。
- 到着順や端末時計だけでは並行性を判定しない。ベース版・親イベント・因果関係を記録する方式を詳細設計で定義する。
- マスターの重複登録は候補を自動検出するが、統合はユーザー判断。統合元IDから統合先IDへの対応関係を維持する。
- Issue・添付ファイルは論理削除を基本とし、削除・復元をイベント化。削除と編集の競合を安全に処理する。
- 添付ファイル実体は上書きせず、差し替え時は新しいIDで保存する。ローカルキャッシュ解放と共有原本の削除は別操作。

## 6. 添付ファイル

添付ファイル本体と登録イベントは別々に到着し得る。メタデータが先に届いた場合は「同期待ち」と表示し、実体を受信後にサイズ・SHA-256等で検証する。A→Bでは既存キャッシュを保持するか解放するか確認し、未送信ファイルは解放しない。B→Aでは必要容量を見積もり、ダウンロード完了まで「オフライン保存準備中」とする。

**検証課題:** OneDrive Files On-DemandとSharePointショートカットの挙動、ファイル取得・解放の自動制御、全ファイルのメタデータ列挙負荷。期待する挙動を実機で確認するまでは実現保証しない。

## 7. スナップショットと長期オフライン復帰

- 通常は差分同期。長期間オフラインで必要な差分が失われた場合は、検証済みスナップショットと後続イベントから再構築する。
- スナップショットには各デバイスの反映済みイベント位置を記録し、日時だけで優劣を判定しない。
- 条件を満たした任意のPCが作成できる。経過期間と変更量を組み合わせて作成を判断する。閾値は未定。
- 複数PCによる並行作成を許容し、固有IDと検証済みメタデータで識別する。共有の単一可変ファイルを奪い合わない。
- 再同期時は未送信のローカル変更を保護し、SQLiteを無条件に上書きしない。
- 古いイベント・スナップショットの自動整理は、復旧可能性・バックアップ・長期オフライン端末への影響を確認できる安全な条件が成立した場合のみ行う。条件を証明できなければ削除を延期する。

**未解決の設計論点:** 全デバイスの変更をどこまで把握できるか、スナップショットの因果的一貫性、休眠PCの扱い、履歴削除を許す条件。技術検証前に削除自動化を実装しない。

## 8. バックアップ・復旧

- SQLite Online Backup APIで1日1回取得。停止していたPCは次回CIM起動時に未実施分を補完。
- ローカルは直近7日分、SharePointは日次7・週次4・月次3世代を暫定目安とする。PCごとに管理。
- 新PCは原則スナップショット＋差分から初期化。必要時にはSQLiteバックアップから復元する。
- 復元時のデバイスID、送信済みイベント、未送信イベントを確認し、二重送信・データ欠落を防ぐ。
- SharePointへのバックアップ保管だけでは独立した災害対策とは限らない。誤削除・同期伝播に備えた保護と復旧手順を別途検証する。添付実体のバックアップ範囲も詳細設計で確定する。

## 9. バージョン・運用UI

- DBスキーマとイベント／スナップショット形式のバージョンを別々に管理。
- 互換性のある形式は同期を継続し、未対応形式や依存イベントは安全に保留する。
- 通常画面は簡易な同期状態表示、詳細画面で未送信・取込待ち・エラー・競合を確認する。
- 「ローカル保存済み」「共有フォルダーへ書出済み」「他PCで受信済み」「SharePointアップロード確認済み」を混同しない。検証できない状態を「全端末同期完了」と表示しない。

## 10. 既存設計との差分と変更管理

現行ドキュメントは同期追加前の初期版仕様。同期機能を実装するまでは既存の動作を維持する。

- `requirements.md`: 共有・オフライン・競合・バックアップ・復旧の要件追加。
- `basic_design.md`: SharePoint/OneDriveを用いた構成追加。
- `database_design.md`: Outbox、イベント適用記録、競合、論理削除、ID統合、同期位置等を追加。
- `api_design.md`: 同期状態、競合解決、オフライン保存設定等を追加。Attachment DELETEの意味を見直す。
- `ui_design.md`: 同期状態・競合・キャッシュ選択UIを追加。
- `detailed_design.md` / `test_design.md`: アルゴリズム、障害時処理、受入試験を追加。
- ADR: SharePoint/OneDrive同期採用の理由と制約を新規記録。

**既存文書の注意点:** `requirements.md` 9.10は「初期版では物理削除を行わない」。一方、`database_design.md` 5.4はAttachmentを「削除可能」とし、`api_design.md` 13.4はAttachment本体・管理情報を削除すると記載。同期追加時に整合性を取る必要がある。さらに既存のIssue削除不可・マスター画面削除なしという初期版仕様と、将来の論理削除機能を区別する。

**導入前の合意事項:** `requirements.md` 8.4の「Windows固有機能への依存は避ける」とOneDrive利用方針の整合性、および3章に挙げたエリア・設備等の既存モデルにないマスターデータを同期対象に含めるか、その扱いを合意する。これらを本方針書だけで確定しない。

## 11. 実装開始のゲート

技術検証の合格と既存CIMへの導入承認は別のゲートとする。

1. 技術検証ゲート: 技術検証計画書の必須試験に合格し、イベントプロトコル、復旧手順、破損時の停止条件、削除保留条件を文書化する。実機検証が必要な機能は未検証と明示する。
2. 導入承認ゲート: 10章の合意事項を解決し、既存の要件定義書・関連設計書を更新して合意を得る。そのうえで導入承認を得た機能のみ、既存CIMへ段階導入する。技術検証の合格だけで既存CIMへの実装・導入を開始しない。
