# CIM SharePoint/OneDrive同期 技術検証計画書（案）

- 作成日: 2026-10-15
- 状態: 実施前（試験結果なし）
- 目的: 既存CIMのDBを変更する前に、ファイル同期をイベント転送路として安全に使えるか検証する。

## 1. 検証環境

- Windows 11 PC 2台相当（可能なら物理PC 2台。仮想PCを使う場合は差異を記録）。
- 同一SharePoint `CIM-Shared` を各PCのOneDriveクライアントで同期。
- 各PCに独立したローカルSQLiteと検証用送受信プログラムを用意する。
- 既存CIMの本番・開発DB、既存ホテルフォルダーは使わない。
- SharePointショートカットと通常の同期設定のどちらを使うか、OneDrive Files On-Demandの設定、クライアント版、通信条件を記録する。

## 2. 検証用最小データモデル

- `device_id`, `event_id`, `batch_id`, `sequence`, `entity_id`, `field`, `value`, `base_revision`, `schema_version`, `created_at`。
- ローカルSQLiteに業務レコード、Outbox、適用済みイベントID、競合記録を持つ。
- バッチは不変。マニフェストにはファイル名、サイズ、ハッシュ、件数を含める候補とする。
- すべての試験でイベントの重複適用ゼロ、受信済み変更の欠落ゼロを確認する。

## 3. 検証シナリオと合格基準

| ID | 試験 | 合格基準 |
|---|---|---|
| T01 | PC-Aで変更、PC-Bへ配信 | PC-Bで同じ変更を一度だけ適用。遅延と各段階の状態を記録 |
| T02 | A/Bで同時に別Issue編集 | 双方の変更が最終的に保持される |
| T03 | 同じIssueの異なるフィールドをオフライン編集 | 独立フィールドを自動統合し値が失われない。統合結果の業務ルールを適用前に検証し、Target Type・Room・Targetの組み合わせ等が不成立の場合は適用を保留 |
| T04 | 同じフィールドをオフライン編集 | 一方を黙って上書きせず競合として保留できる |
| T05 | 同一イベント／バッチを再読込 | 重複適用せず副作用も重複しない |
| T06 | バッチ転送途中・不完全ファイル | 不完全なデータを適用せず、完成後に再試行できる |
| T07 | ファイル到着順序逆転・依存イベント未着 | 依存関係を満たすまで保留し、後で正常適用 |
| T08 | OneDrive停止、ネット切断、再接続 | ローカル変更を失わず、再開後に収束 |
| T09 | PC強制終了（書出前／途中／適用中） | Outboxと適用記録が一貫し、再起動後に再試行可能 |
| T10 | 未対応形式・破損・ハッシュ不一致 | 安全に保留／隔離し、既存データを破壊しない |
| T11 | 添付登録イベントが実体より先に到着 | メタデータ表示後に待機し、実体到着後ハッシュ確認 |
| T12 | 添付実体がイベントより先に到着 | 不要なIssue登録をせず、イベント後に正しく関連付け |
| T13 | プロジェクトA/Bオフラインキャッシュ切替 | 未送信実体を削除せず、Aの完全取得を確認して表示 |
| T14 | スナップショットを複数PCで並行作成 | 衝突・上書きなし。各スナップショットの適用位置を検証 |
| T15 | 長期オフラインPCの復帰 | 未送信変更を保護し、再同期で欠落・無断上書きなし |
| T16 | バックアップ作成中のDB更新／復元 | 一貫したDBに復元でき、イベントの重複を防止 |
| T17 | SharePoint上の削除・誤操作・権限喪失 | データ消失リスクと復旧方法を実測・記録。自動削除は未承認のまま |
| T18 | OneDriveのショートカット／Files On-Demand | プレースホルダー、容量、取得・解放、ファイル数負荷を実測 |

## 4. 実施順序

### Phase 0: 事前準備

検証専用共有フォルダー、検証用端末、ログ採取、サンプルデータを用意する。既存CIMは変更しない。

### Phase 1: ファイル転送の安全性（最優先）

T01、T05～T10を実施。イベントバッチが不完全・重複・順不同に到着しても安全に扱えるかを確認する。**ここに不合格があればCIM統合へ進まない。**

### Phase 2: オフライン・競合

業務同期検証の開始前に、方針書3章の未決事項（User・Roleの同期範囲、共通ID、登録者・更新者等の参照解決）を設計し、検証項目・合格基準を定める。Roleを同期する場合は、オフライン中の並行変更でもAdministratorを最低1人維持できることを検証対象に含める。現時点では方式を確定しない。

T02～T04、T15を実施。SQLite Outboxの永続性、因果関係、手動競合解決を確認する。

### Phase 3: 添付・容量

T11～T13、T18を実施。A/Bキャッシュ設定の実現可能性を判断する。自動キャッシュ制御が困難なら代替設計を提示し、実装前に承認を得る。

### Phase 4: スナップショット・バックアップ・運用

T14、T16、T17を実施。特に履歴自動削除は復旧安全性を証明するまで有効化しない。

## 5. 観測・記録項目

- OS、OneDrive版、SharePointフォルダーの同期方法、Files On-Demand設定。
- ファイル生成時刻、書出確定時刻、他PC検出時刻、適用時刻。**SharePointアップロード完了は独立に観測できた場合のみ記録。**
- 送受信イベント数、重複数、保留数、競合数、エラー数、再試行回数。
- 同期前後の業務データ内容・ハッシュ、添付のハッシュ。
- 切断・再起動・容量不足・権限エラー時の挙動。
- ストレージ消費量、プレースホルダー数、初回同期時間。

## 6. Go / No-Go判定

**Go（技術検証）:** Phase 1の必須安全試験に合格し、データ損失なし・冪等性・障害再開・保留／隔離が再現できる。続いて各Phaseの対象機能を検証する。技術検証の合格は既存CIMへの導入承認を意味しない。

**導入承認（別ゲート）:** 方針書10章の合意事項（Windows固有機能への依存を避ける既存要件とOneDrive利用方針の整合性、既存モデルにないマスターデータの扱いを含む）を解決し、既存の要件定義書・関連設計書を更新して合意を得る。方針書11章の条件を満たし、導入承認を得た機能のみ既存CIMへ段階導入する。

**No-Go:** イベント欠落、無断上書き、重複副作用、不完全ファイルの誤適用、未送信変更の消失が再現する場合。原因解消・再試験まで既存CIMに組み込まない。

**条件付き:** SharePointアップロード完了の確証、Files On-Demand自動制御、履歴削除の安全性などが未検証の場合、その機能の実装・表示・自動化を保留し、限定した運用で進める。

## 7. 実装計画（検証後）

以下は6章の技術検証・導入承認の両ゲートを満たした後に開始する。

1. イベント形式・ID・Outbox・冪等な取込処理を独立モジュールとして実装。
2. 同期フォルダー設定とバッチの安全な発行・受信・再試行を追加。
3. Issue・Comment・マスターの同期と競合UIを段階追加。
4. 添付実体同期とプロジェクト別オフライン保存設定を追加。
5. スナップショット、再初期化、バックアップ／復元を追加。
6. 保持・整理機能は安全条件を実証した範囲で段階導入。

各段階で既存テストを維持し、マイグレーションは既存Alembic履歴を改変せず新規リビジョンとして追加する。

## 8. 未確定事項

イベント因果メタデータの詳細、バッチ確定・公開プロトコル、再試行間隔、競合UI、スナップショット整合性の証明方法、休眠PCの扱い、履歴整理条件、OneDrive APIを使わないキャッシュ制御の実現性、添付実体の独立バックアップ方法。これらは検証結果を踏まえて決定する。
