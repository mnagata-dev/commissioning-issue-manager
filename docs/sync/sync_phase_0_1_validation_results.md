## 2. 検証だけに使用した仮方式

- 合成レコードは `entity_id`、文字列 `value`、最新イベントIDを保持する。実際のIssueや業務ルールは扱わない。
- 計画書2章のイベント項目を使用する。1イベント＝1バッチとし、イベントIDをバッチIDに兼用。これらは検証用の簡略化であり正式仕様ではない。
- 業務相当レコードとOutboxを同一SQLiteトランザクションで保存する。
- JSON Lines実体を `.part` に書き、実体ファイルへ置換した後、サイズ・SHA-256・件数・版・バッチIDを含むmanifestを公開する。
- Outboxの送信済みはローカル公開後に記録する。他PC受信やSharePointアップロード完了を意味しない。
- 受信時はmanifestと実体を検証してから適用する。実体未到着・不完全なら保留し、到着・修復後に同じ入力を再試行する。
- 破損・不正形式は内容ハッシュ名で受信側quarantineへコピーし、受信原本を残す。隔離コピーは診断用。サイズ・ハッシュ不一致は転送途中と区別できないため保留も継続する。
- 未対応版は原本を保持して保留する。自動変換しない。
- 適用済みイベントIDと内容を保存し、重複は無操作。同じIDで異なる内容は隔離する。
- `base_revision` は当該レコードの直前イベントIDとする。未到着の依存または競合は保留する。両者の識別・競合解決は今回実装しない。
- レコード更新、適用済みID、副作用を模したeffects行を同じトランザクションで確定する。副作用数の不変性を重複試験で確認する。

manifest公開自体の原子性を前提にしない。読み取り途中の不正JSONも隔離・再試行対象となる。自動監視、再試行周期、イベント集約、プロトコルの正式決定は対象外。

|T09|下記8か所で別プロセスを終了コード73により即時終了。保存のロールバック、公開再開、適用の原子性、commit後の重複排除を確認|プロセス中断範囲で合格|Windows強制終了、OS停止、電源断、ストレージ障害は未検証|
|T10|不正JSON、配列、必須項目不足、型不正、未対応フィールド、不正manifestを隔離。manifest／イベントの未知版は保留。サイズ一致の実体改変でもハッシュ不一致を検出。修復後に適用可能。同じIDの内容改変は既存データを変更しない|ローカル合格|ファイルロック、権限喪失、容量不足、悪意ある入力全般は未検証|

T09の中断位置:

- ローカルレコード書込み後・Outbox保存前: レコードとOutboxの両方が未確定のままロールバック。
- ローカルcommit直後・書出前: 未送信Outboxから公開・受信まで再開。
- `.part` の半分を書いた後: manifest・完成実体が存在せず、Outboxから書き直して再開。
- 完成実体の公開後・manifest前: 再公開して受信まで再開。
- manifest公開後・送信済み記録前: 同一内容で再公開して受信。再受信でも副作用1件。
- 受信レコード更新後・適用済みID記録前: 受信DBのレコード・適用履歴・副作用をまとめてロールバック。
- 適用済みID・副作用記録後・commit前: 同様に全体をロールバック。
- 受信commit直後: 再受信を重複として扱い、適用・副作用各1件。

合成した正常イベントの欠落、重複副作用、不完全ファイルの適用、未送信変更の消失は観測されなかった。任意の障害組合せを保証する結果ではない。

## 5. 発見事項と残るリスク

- ローカルで再現した必須安全条件に不合格はなかった。
- ハッシュ不一致だけでは、転送途中と永続的破損を区別できない。今回の仮方式は原本を保持して再試行する。実運用向けの再試行上限、通知、隔離容量管理、修復手順は未決定。
- 依存待ちと競合を同じ保留状態とする簡略方式。永久保留の検知、複数端末の因果関係、User・Roleの参照解決、実際の業務ルールは検証していない。
- `os._exit` はPythonの終了処理を行わないプロセス中断であり、OSキャッシュ喪失や電源断ではない。ディレクトリエントリーやmanifestの耐電源断性を保証しない。
- 受信側の隔離・SQLite書込み・ファイル読取り中のI/Oエラーや同時アクセスの網羅試験は行っていない。
- サイズ・ハッシュは転送完全性の候補であり認証ではない。信頼境界、入力サイズ制限、不正な送信者への対策は別検討が必要。
- 1イベント1バッチかつ少数の合成データ。多数ファイル、バッチ集約、容量、性能、Files On-Demandの評価結果ではない。
- 既存方針書10章の要件・設計上の合意事項は未解決のまま維持する。今回の結果で既存文書や仕様を変更しない。

## 6. 次工程の判断

**条件付きで、独立したWindows 11・OneDrive・SharePoint実機検証の準備へ進める。** 今回の模擬範囲で修正が必要な不合格はない。ただしPhase 0の実機環境準備、およびPhase 1の実機T01・T05〜T10は未完了。技術検証ゲートの合格とはしない。CIM統合やPhase 2への移行判断は行わない。

次の実機試験では検証専用SharePointフォルダーと2台のWindows PCを用意し、OS・OneDrive版・同期方式・Files On-Demand設定を記録する。実際の同期クライアントを転送路に使い、manifest／実体の到着順、部分状態、停止・再開、強制終了時の保持・再試行を確認する。ローカルコピーによる所要時間を実機の性能根拠にしない。

このプログラムは自動試験用の部品であり、実機用の監視・手動送受信CLIは含まない。実機試験前に最小の操作手順と記録方法を用意する必要がある。実機で欠落・無断上書き・重複副作用・不完全適用・未送信変更消失を観測した場合はNo-Goとし、原因解消と再試験まで統合しない。
